# VIEWTV 0034 — prueba Win32 de doble handle NTFS: avance y bloqueo de seguridad

**Fecha:** 28/11/2026. **Rama:** `viewtv-seguimiento-descargas-0012`; PR #2 OPEN/DRAFT, sin merge. **Ámbito:** código y ejecución de pruebas **solo en directorios TEMP GUID y archivos totalmente ficticios**. Las funciones importadas de 0016 consultan la publicación real **solo en modo Audit**; jamás se escriben ni eliminan originales, copias multimedia, torrents, cachés ni diarios productivos.

## Problema que impedía cerrar el borrado

El diseño original validaba que un `FileStream` con `FileShare.None` bloquea lectores de cualquier nombre del mismo File ID NTFS. Pero para eliminar ambos hardlinks por rutas distintas era necesario soltar ese handle y se abría una ventana de reapertura. El hito 0034 comprueba si se pueden preparar **dos handles DELETE** sobre los nombres exactos y ejecutar ambos `unlink` sin ceder capacidad de lectura/escritura.

## Ensayos Windows reales sobre archivos ficticios

- `scripts/viewtv_windows_ntfs_exclusividad_sandbox_0034.ps1`: crea dos hardlinks de un archivo aleatorio TEMP, verifica volumen/File ID/longitud/nlinks exactos; un lector ya abierto bloquea adquirir `FileShare.None`, y la reserva exclusiva bloquea nuevos lectores y escritores por ambos nombres. Rechaza un tercer hardlink observado. Sin embargo, **`CreateHardLinkW` consigue crear un tercer enlace incluso mientras el archivo está abierto con `FileShare.None`**. Esta es una brecha de metadatos independiente de los handles de datos.
- `scripts/viewtv_windows_ntfs_dual_handle_sandbox_0034.ps1`: abre ambos nombres ficticios mediante Win32 `CreateFileW` con `DELETE|FILE_READ_ATTRIBUTES` y `FILE_SHARE_DELETE`, verifica con `GetFileInformationByHandle` que ambos handles son el mismo File ID, sin reparse y exactamente dos enlaces. Nuevos lectores de ambos nombres fallan. Con `SetFileInformationByHandle(FileDispositionInfoEx, DELETE|POSIX_SEMANTICS)` **los dos `unlink` de prueba funcionan manteniendo vivos ambos handles**. Se simula una interrupción después del primer `unlink` soltando los handles, se coteja el File ID del superviviente y se restaura el primer hardlink, luego se vuelve a adquirir el par y se completan los dos `unlink` ficticios.
- El mismo ensayo demuestra **`TERCER_LINK_DURANTE_RESERVA=POSIBLE`**: la doble reserva con `FILE_SHARE_DELETE` tampoco bloquea a otro proceso que pueda crear otro hardlink. El tercer enlace se crea y elimina **solo dentro del sandbox**, restaurando el par ficticio antes de continuar.
- El ensayo registra siete estados en un diario TEMP `jsonl` con `FileOptions.WriteThrough` y `Flush(true)` y verifica orden, versión y File ID. Es una **simulación de cierre/reapertura de handles en el mismo proceso**, NO una prueba de apagón o muerte abrupta del proceso; el diario TEMP no tiene todavía las ACL ni firmas exigidas al ejecutor Windows.
- `scripts/test_viewtv_windows_ntfs_kernel_0034.ps1`: ejecuta los dos scripts en procesos PowerShell separados, comprueba **todas las líneas de salida esperadas y el código de salida**, y rechaza evidencia incompleta. Resultado: `NTFS_0034_DOS_SUITES_SANDBOX=PASS`, `NUEVOS_HARDLINKS_CON_LOCK_PUEDEN_APARECER=SI`, `PREPARADO_PARA_BORRADO_REAL=NO`, **0 archivos reales eliminados, 0 torrents reales modificados**.
- Regresión posterior: **backend 1572/1572 PASS**, 2 advertencias externas; TypeScript PASS, ESLint PASS, smoke real read-only **10/10 PASS**. Preflight real: **4/4 películas bloqueadas**, **2/2 diarios NTFS verificados**, 0 archivos eliminados y 0 cambios de torrents. Ruff global sigue fallando con **128 hallazgos heredados**; ningún fichero Python de este hito se ha alterado. `git diff --cached --check` limpio.

No hay rutas ni IDs productivos en los parámetros; ninguno de los tres scripts acepta argumentos. Antes de limpiar ficheros TEMP comprueban raíz GUID, marcador y ausencia de reparse/elementos desconocidos. Solo crean, restauran y eliminan nombres recién creados en esa carpeta de ensayo.

## Otro hallazgo relevante en producción (solo lectura)

La comprobación `Get-CimInstance Win32_Process` + `Invoke-CimMethod GetOwner` demuestra que **Jellyfin nativo y qBittorrent nativo usan la misma identidad de Windows que la sesión desde la que se inspecciona VIEWTV**. No se publicaron nombres de usuario ni credenciales. Por tanto, **una ACL que deje escribir a esa misma identidad no separa a qBit/Jellyfin de un borrador que use ese mismo usuario**. Tampoco basta negar apertura de datos si el mismo usuario puede crear nuevos nombres NTFS.

Esta evidencia no equivale a haber probado que Jellyfin nativo sirva exactamente los mismos archivos, pero impide afirmar exclusión de procesos por identidad. La auditoría 0033 observó reglas de entrada amplias y listeners nativos; siguen sin demostrarse los accesos efectivos desde LAN.

## Gate real que sigue faltando (NO crear atajos)

1. **Separar identidades y capacidades:** un servicio/broker Windows de retirada con identidad propia, controlada, mínimo privilegio y ACL de directorios/archivos protegidas. qBittorrent, Jellyfin nativo y otros lectores deben estar efectivamente segregados del permiso de cambiar enlaces de los File ID seleccionados. Comprobar con tokens de otros SIDs que `CreateHardLinkW` no puede crear enlaces nuevos desde ninguna ruta permitida durante la retirada. No basta un mutex entre procesos colaboradores.
2. **Custodia de descarga única:** correlacionar el torrent exacto con el diario de publicación, impedir reanudación y nuevas escrituras antes y durante el commit, sin alterar los cuatro metadatos extras de qBit (488 bytes lógicos). El código 0026 es solo lectura; el mecanismo transaccional no está desplegado.
3. **Bloquear reproducción real:** sustituir HLS v1 por v2 y activar el guard en todas las rutas, incluidos directos/segmentos/Range, cerrando el acceso directo a Jellyfin sin interrumpir clientes legítimos. Los laboratorios 0029–0032 no están desplegados.
4. **Administrador y transacción física:** identidad administrativa separada (0019 aún no enrolada en producción), aprobación específica ligada a película/descarga/evidencia, diario Windows protegido y fsync con consumo único, reconciliación tras `kill` y reinicio reales, reserva de ambos handles y exclusión de nuevos hardlinks hasta liberar ambos nombres, medición de bytes físicos en el mismo volumen. Revalidar estado HLS, qBit, identidad NTFS, ausencia de terceros y permiso admin **en el instante de la operación**, bajo un protocolo durable completo.
5. **Primera retirada:** sólo una película **concreta**, todos los perfiles vistos, petición válida, torrent completo/custodiado, dos diarios NTFS comprobados, sin ficheros extra afectados y aprobación expresa del propietario. El preflight real anterior seguía con **4/4 películas bloqueadas**, cero aprobaciones, cero borrados; no existe una candidata actual.

**Resultado del hito: método de eliminación por dos handles y reconciliación ensayados, pero NO aislamiento definitivo.** Es inseguro activar el borrado real mientras otro actor pueda crear nuevos hardlinks al mismo File ID o abrir el origen por una vía externa. PR #2 se mantiene OPEN/DRAFT. Samsung y Momentos siguen pospuestos hasta cerrar el sistema de retirada seguro.
