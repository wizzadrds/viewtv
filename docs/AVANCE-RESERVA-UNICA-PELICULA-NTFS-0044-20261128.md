# VIEWTV 0044 — autorización administrativa consumida una sola vez por película y File ID NTFS

**Fecha:** 28/11/2026. **Rama:** `viewtv-seguimiento-descargas-0012`, PR #2 OPEN/DRAFT, sin fusionar. **Ámbito:** un laboratorio Python/SQLite privado y `httpx.MockTransport` del ensayo 0038; nunca se conecta al qBittorrent real ni dispone de modo de eliminación física. No se instalan servicios, ACL ni credenciales de administrador.

## Brecha subsanada respecto al hito 0019

El 0019 ya verifica una **firma offline HMAC-SHA256** sobre una película, descarga, nonce, plazo de 600 segundos y huella del preflight; el consumo de ticket exige una SQLite privada y `PRIMARY KEY(nonce)`, por lo que el mismo ticket no se puede consumir dos veces. **No prohibía almacenar otra firma válida para la misma película con otro nonce** y no había una reserva SQL con unicidad por File ID, torrent y descarga compartida con la custodia qBit.

El hito 0044 agrega ese tramo transaccional como laboratorio independiente **y endurece el consumidor administrativo existente del 0019**: ahora `consumir_ticket_una_vez()` crea índices únicos sobre `medio_id` y `descarga_id` dentro de la transacción SQLite, además de la unicidad por nonce. Un segundo ticket válido con nonce distinto no puede reautorizar el mismo medio ni reutilizar la misma descarga. Si una tabla histórica contiene duplicados, falla sin alterarlos. El servicio activo y la API siguen sin importar este procedimiento; el ticket, por sí solo, no autoriza borrado.

Compara tamaño del archivo de video publicado en el diario con el tamaño NTFS y exige una sola publicación. La huella se serializa en JSON canónico con dominio `VIEWTV_0044_SOLO_SANDBOX` y se firma con el contrato existente del 0019, usando **solo una clave sintética** en tests.

Cualquier duplicación, incluso con nuevo ticket, falla cerrada.

## Límite decisivo para el borrado productivo

**La reserva SQLite del 0044 y el ledger administrativo independiente del 0019 todavía NO son una transacción global compartida**. El 0044 comprueba HMAC y consume su propia reserva, mientras que el 0019 protege de manera separada la unicidad de su propio diario. Un ejecutor futuro tendrá que centralizar y revalidar ese consumo, sin aceptar un ticket usado en otro ledger. Este laboratorio **no está integrado en un ejecutor de Windows** y la información de File ID procede de un testigo ficticio suministrado por el propio ensayo, **no de una DACL/consulta kernel confiable al instante de commit**. No bloquea el acceso a qBit por WebUI/GUI, ni impide lectores de Jellyfin directo o HLS v1, ni excluye hardlinks creados por otros procesos. La coincidencia de dos consultas no es exclusión; entre ellas o después puede cambiar el estado. La misma SQLite solo coordina los procesos de VIEWTV que usan efectivamente esa transacción; los procesos y clientes ajenos no participan.

Además siguen pendientes un broker Win32 con SID independiente y ACL efectiva para **un File ID**, cierre controlado de WebUI y drenaje Jellyfin sin romper la reproducción legítima, administración independiente con clave real fuera del repositorio, autorización expresa de **una película específica**, coherencia atómica entre fuentes, restauración tras apagón eléctrico real, validación final de todos los enlaces y la medición física de espacio libre. **No dar permiso de borrado ni fusionar/desplegar la PR solo por superar estas pruebas.**

**La primera retirada productiva no puede hacerse mientras el preflight 0018 mantenga las cuatro películas bloqueadas y el interlock 0041 no verifique aislamiento kernel.** En 0044 no se ha detenido ningún torrent, modificado fichero real, cambiado puerto o ACL, ni eliminado película.
