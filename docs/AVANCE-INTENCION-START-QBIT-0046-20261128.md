# VIEWTV 0046 — intención START durable anterior a qBittorrent (solo sandbox)

**Fecha:** 28/11/2026. **Rama:** `viewtv-seguimiento-descargas-0012` — PR #2 abierta y en borrador, no fusionar. **Sin despliegue, eliminación de películas, parada de torrents reales ni cambios en qBittorrent/Windows/Jellyfin.**

## Falla de carrera resuelta en la vía simulada de VIEWTV

El cerco 0039 coordinaba un `POST /api/v2/torrents/start` con un `BEGIN IMMEDIATE` de la misma SQLite utilizada para registrar la custodia de retirada. Mientras ambos procesos permanecían vivos, se evitaba la carrera: el primero obtenía el bloqueo y el segundo debía esperar. **Pero si el proceso moría durante el POST, SQLite revertía la transacción y no quedaba un rastro durable de la orden START**. Un snapshot anterior del torrent podría permitir que se registrara su custodia después, aunque el servidor ya hubiese comenzado a ejecutarlo.

El 0046 cambia ese orden: **persistir primero la intención de START y confirmar el COMMIT antes de permitir que se emita el POST simulado**. Si el START se confirma, la bitácora conserva `confirmada`; ante respuesta perdida, muerte o cualquier fallo durante el envío queda `pendiente`. **Ambos estados bloquean permanentemente la inscripción de custodia del mismo hash, incluso tras reiniciar**. No existe expiración de esta barrera ni un borrado automático de la intención. Se exige una reconciliación específica posterior que todavía no se ha implementado: se prefiere impedir un retiro seguro a dar un falso permiso.

## Cambios de código

- `worker/retirement_qbit_start_intent_lab_0046.py` define una tabla `inicios_qbit_0046` de hash exacto y estado, comprobando su definición SQL y registros antes de operar. La clave primaria utiliza `COLLATE NOCASE` para evitar duplicados de hash en diferentes mayúsculas. **Sin opción para limpiar la intención, borrar medios, alterar qBit real ni otorgar permiso físico**.
- `worker/retirement_qbit_stop_lab_0038.py`: al crear una base **nueva** registra la tabla de intenciones en el mismo SQLite privado que `custodia`. Una base **existente** que haya perdido la tabla de START **no se recrea silenciosamente** y bloquea el laboratorio; esto evita que una tabla eliminada o un fichero de formato anterior esconda órdenes inciertas. `registrar` comprueba bajo su misma transacción que el hash de película no tenga ninguna intención previa. No afecta a torrents de otros hashes.
- `worker/retirement_qbit_start_fence_lab_0039.py`: dos transacciones: primero verifica que el hash no está custodiado y **confirma una fila `pendiente`**; después, aún con bloqueo de escritura, verifica el cliente `httpx.MockTransport`, emite el POST y, si termina correctamente, marca `confirmada`. Una caída antes del POST deja la intención `pendiente`; una caída durante o después del POST, antes de confirmar el estado, también deja `pendiente`. Cualquier repetición de ese START se rechaza sin reenvío. El método de observación `estado_intencion` responde siempre con `puede_borrar_archivos=False`.
- `backend/tests/test_qbit_start_fence_lab_0039.py`: el test anterior de orden START primero ahora exige **rechazar el alta de custodia tras el POST** (antes se permitía). Es un cambio intencionado de seguridad y no una regresión.

## Qué sigue SIN resolver y por qué el borrado permanece BLOQUEADO

La nueva bitácora solo intercepta START del adaptador VIEWTV simulado. **Ni la GUI nativa, ni otros clientes de la WebUI ni los reinicios autónomos de qBittorrent participan en esa SQLite**. Las dos consultas GET no forman una exclusión real. El ordenador actual comparte SID entre qBit/Jellyfin/publicador y su firewall mantiene vías amplias; los HLS v1 y Jellyfin directo todavía permiten accesos alternativos. El ensayo de SID 0037 no ha modificado ACL reales, y el 0034 demostró que incluso dos handles Win32 DELETE abiertos no impiden crear un tercer hardlink sin una DACL apropiada. Falta el servicio broker Win32 de identidad independiente, control de credenciales y rutas qBit, admisión/drenaje reales de reproducción, autorización offline por película, File ID protegido al instante de commit y ejecutor con capacidad de recuperar tras pérdida eléctrica y demostrar espacio liberado.

El `interlock 0041` sigue expresando seis barreras productivas pendientes. El último preflight del equipo mantiene **cuatro películas bloqueadas y cero candidatas aptas**, dos torrents sin reposo seguro y cuatro archivos auxiliares protegidos, sin operaciones destructivas. **El objetivo de una retirada real sigue prohibido hasta tener una película elegible, autorización expresa de su administrador y aislamiento probado.** El 0046 es una corrección de seguridad en laboratorio; no habilita ni instala ningún ejecutor de borrado.
